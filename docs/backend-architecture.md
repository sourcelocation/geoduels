# Backend architecture

GeoDuels backend code has exactly three application layers:

```text
transport handler -> domain service -> domain-owned store interface
                                            ^
                                            |
                              PostgreSQL/sqlc implementation
```

## Dependency rules

- Handlers decode transport input, authenticate the caller, invoke one domain
  service operation, and map domain results to transport responses. Handlers do
  not import PostgreSQL packages, inspect `pgx` errors, or receive a database
  store.
- Services own authorization beyond transport authentication, validation,
  policy, orchestration, domain models, and domain errors. A service may depend
  only on the narrow store interfaces declared by its own domain package.
- Store interfaces describe use-case persistence capabilities, not tables or
  generic CRUD. Business/domain packages never import a concrete persistence
  package.
- PostgreSQL implementations translate between domain and generated sqlc
  types. Runtime SQL exists only as named queries under `db/queries`; generated
  code lives under `pkg/persistence/sqlc` and is gitignored — regenerate it
  with `go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.30.0 generate`.
- Caller contexts flow unchanged from handlers and workers through services and
  stores. Request-driven code must not replace them with background contexts.
- Atomic workflows are concrete store methods implemented with
  `Queries.WithTx`. Services request an atomic domain operation and never receive
  `pgx.Tx`.

## SQL ownership

The following are the only intentional SQL sources:

- forward-only migrations under `db/migrations` (also the sqlc schema input —
  there is no separate, hand-maintained schema projection);
- named sqlc queries under `db/queries`;
- code generated by sqlc under `pkg/persistence/sqlc` (gitignored, regenerated
  in CI and Docker builds).

Executable SQL literals and direct `Query`, `QueryRow`, `Exec`, or `Prepare`
calls are forbidden in all other Go production code. Connection creation,
health checks, transaction begin/commit/rollback, and `Queries.WithTx` are the
only database primitives allowed in handwritten PostgreSQL infrastructure.

## Composition

Process composition roots construct concrete PostgreSQL stores, inject them
into domain services, and inject services into handlers/workers. They must not
retain a general-purpose store that handlers can bypass. There is no aggregate
`persistence.Store` application dependency.

## Verification

Regenerate sqlc code, then run `go test ./...` and `go vet ./...` before
completing backend changes.
